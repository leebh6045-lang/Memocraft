# 仓库内容与公开政策

## 1. 判断原则

公开仓库应让新读者了解产品目的、当前状态、实现方式和验证方法。依据内容是否有助于复现与维护决定是否提交，而非一概排除开发文档。

| 内容                                                 | 处理                                   |
| ---------------------------------------------------- | -------------------------------------- |
| README、产品规格、架构、开发准则、项目结构与工具约定 | 放在公开 docs 中，随实现维护           |
| 源码、必要配置、锁文件、迁移、无隐私的测试样例       | 提交                                   |
| 有持续维护价值的设计决策与最终设计说明               | 脱离会话语境整理后提交                 |
| 原始个人想法、会话推导、历史规划、机器环境记录       | 本地保留，不提交                       |
| 临时 HTML 原型、截图、验证脚本和设计比较材料         | 统一放 .local 中，不提交               |
| 用户数据库、附件、备份、导出、日志和凭据             | 不提交                                 |
| 依赖、构建产物、测试报告、安装包                     | 不提交源代码仓库；正式发行另走发布流程 |

## 2. 文档唯一来源

README、项目协作指南.md 与 docs 下的规范构成可在新克隆中完整阅读的公开文档。后续产品和工程决定更新这套文件。

本地保留的早期根目录 Markdown 与历史资料是参考材料，不再与公开规范平级维护。公开文件不得链接到被忽略的必读文件，不包含原始会话、个人设备用户名、绝对本机路径或未核验的环境声明。

项目协作指南.md 保留协作规则而不保留私人背景。不同代理应从公开入口读取相同规范，不依赖某次会话的个人上下文。

## 3. 临时原型

临时界面设计放在 `.local/prototypes/`。HTML、关联素材和检查截图随该目录整体忽略。原型只用于比较布局与交互，不作为正式前端代码或产品已实现的证据。

不要通过忽略所有 `*.html` 或 `*.md` 来排除原型；正式 Vue 入口 HTML 和公开文档需要正常跟踪。未来采纳方案时，将设计决策与生产实现分别整理到公开目录，不直接把整套临时原型复制进源码。

## 4. Git 提交与公开前检查

1. 使用 `.gitignore` 排除本地资料和生成内容，新增加的私人材料默认放 `.local/`。
2. 在已经初始化的仓库中，先查看 `git status --short`，按具体文件或公开目录暂存；新文件未审查前避免笼统加入全部内容。
3. 提交前查看 `git diff --cached --stat`、`git diff --cached` 和暂存文件列表，检查正文、图片、测试样例、配置及链接。
4. 可用 `git check-ignore -v <路径>` 检查排除规则；确认源码、公开文档和无隐私测试样例没有被误排除。
5. 新增依赖时同时提交清单与锁文件；不提交 node_modules、真实数据或证书。
6. 推送前检查将要公开的提交历史。README 对功能、测试和发布状态的描述须与事实一致。

`.gitignore` 只影响未跟踪文件的默认加入行为，不会抹除已跟踪文件、旧提交或强制加入的内容。如果私人文件已被跟踪，应先确认范围，再停止跟踪并保留本地文件；已经进入公开历史的隐私或凭据需另行处理，不能仅新增忽略规则就宣称已清理。

本政策不自动创建远端仓库、提交或发布内容。签名证书、账号凭据和发布权限由实际工作流程管理。
