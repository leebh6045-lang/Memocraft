# Memocraft 开发准则

> 当前开发规范。项目已进入首轮桌面实现；本文的完整 v1 目标不等于全部已完成。实际范围与验证见 [首轮交付](首轮交付.md)。
> 公开文档入口见 [项目说明](../项目说明.md)，提交范围见 [仓库内容政策](仓库内容政策.md)。

## 1. 四项质量目标

| 目标     | 本项目中的含义                                   | 评审时要回答的问题                                       |
| -------- | ------------------------------------------------ | -------------------------------------------------------- |
| 可读性   | 命名、流程和数据含义清晰，关键原因可追溯         | 不看原会话，能否知道这段代码做什么、为什么这样做？       |
| 健壮性   | 输入无效、写入失败、重复操作和异常退出时行为明确 | 失败后内容是否仍在，能否重试，会不会留下半套结果？       |
| 可维护性 | 修改范围可控，规则有依据，验证可重复             | 改一项规则需要改哪些地方，如何证明没破坏已有行为？       |
| 低耦合   | 各层职责明确，通过有限接口协作                   | 修改页面布局是否需要动 SQL，更换驱动是否需要改四个页面？ |

代码能运行只是基础。也不能为了“架构漂亮”引入大量空接口、透传层和学习负担。优先选择在当前需求下容易解释、验证和修改的最简单方案。

## 2. 需求与修改范围

1. 开始修改前，明确本次用户目标、受影响行为与验收方式，阅读相关实现及其调用方。不能只找到同名函数就直接替换。
2. 以用户当前明确要求和当前规范为依据；本地早期材料只用于追溯，不能据此恢复已取消的设计。
3. 不因“更完善”自行新增产品状态、模块或流程。手记的大分类固定为“收获、思绪、待办、完成、其他”，按此顺序呈现，默认“收获”；不新增独立待办/完成状态，不重新加入整理、问题解决或回顾进度。标签可自由添加，不据此扩展大分类。
4. 修改覆盖实现目标所需的完整链路，包括相关契约、调用方、迁移、测试与文档；“改动小”不意味着留下不一致的接口或未处理的失败路径。
5. 不顺手重写无关模块、移动整个目录、升级全部依赖或格式化整个仓库。确有必要的重构说明原因和影响，尽量与行为变更分开形成可审阅的修改。
6. 发现不影响本次目标的遗留问题，记录具体位置与后果，不扩大当前任务。发现直接影响本次结果的缺陷则在授权范围内修复并验证。
7. 普通命名、局部拆分和错误处理等实现选择自行完成；已授权的工作不重复请求确认。只有无法从上下文确定且会实质改变需求、兼容性或数据处置的分歧，才说明具体问题并向用户澄清。

## 3. 可读性：让代码表达意图

### 3.1 命名与表达

- 项目产出的 Markdown 文档统一使用中文文件名，以内容职责命名，例如 `产品规格.md`、`首轮交付.md`、`001-桌面记录链路.md`；允许必要的编号、日期、版本号和技术专名。已有英文文档改名时，同步维护链接、目录树、代码注释和配置引用。第三方依赖及工具自动生成的报告不手工改名。
- 固定工具入口 `README.md`、`AGENTS.md` 只保留简短说明和中文正文链接，分别服务仓库首页展示与代理自动发现；不在入口中维护第二份正文。
- 业务术语保持一致：Note 是手记，Topic 是归纳（模块名称为“主题归纳”），Thread 是长期事务，ThreadEntry 是动态。不要在同一概念上混用 State、Event、Log 等名字。
- 标识符使用清晰英文，面向用户的文字与解释性注释优先中文。常用缩写如 ID、IPC、SQL 可以使用，自造缩写要避免。
- 函数名说明动作与对象，如 `saveNoteDraft`、`addNoteToTopic`；布尔值表达可判断的问题，如 `isSaving`。禁止依靠 `handleData`、`doStuff`、`flag2` 等名字承载业务含义。
- 稳定 ID 与标题、创建时间与发生时间、固定大分类与自由标签要在类型和命名中区分，不能靠调用者猜测。
- 优先直白控制流、提前处理异常条件和局部变量。避免嵌套三元表达式、带副作用的长链式调用和隐藏顺序依赖的技巧。
- 业务常量有名称和来源；不为普通的 0、1 或只出现一次且含义清晰的文字制造无意义常量。

### 3.2 函数、文件与注释

- 一个函数承担一个可以描述清楚的动作。参数组合复杂时使用具名对象，避免多个位置布尔参数。
- 一个文件围绕一项相关职责组织。文件增长、重复分支或难以解释的依赖是拆分信号；不以固定行数制造机械拆分。
- 注释解释原因、约束、失败恢复或不能随意改变的细节，不逐行翻译代码。修改行为时同步修改注释。
- 现有代码及后续新增、修改的手写代码，均配备精而简的中文注释。重点说明职责边界、关键业务约束、异步顺序、失败恢复与不直观的实现原因，通常用一两句话写在相关声明或逻辑之前。
- 不为每个函数或每一行机械添加注释，不重复清晰命名已经表达的内容，不用长篇注释掩盖难读的代码。类型和符号名保留英文；必要的协议名、工具指令保留原文。行为变化时同步更新或删除过时注释，交付前核对注释与实际代码一致。
- 跨层接口、备份恢复、迁移与并发控制需要必要说明；简单 getter 或显而易见的 UI 事件不强制逐个写长文档。
- 临时方案写清限制与移除条件；禁止没有后果说明的 `TODO: later`、大块注释掉的旧实现和失效示例。已有版本历史承担旧代码留存职责。
- 业务逻辑不塞进模板表达式、深层 watch 或模块导入时自动执行的副作用中。

## 4. 低耦合：分层与依赖边界

目录定义以 [项目结构](项目结构.md)为准，边界按以下规则落实：

| 层         | 应承担的职责                           | 不应承担的职责                                             |
| ---------- | -------------------------------------- | ---------------------------------------------------------- |
| renderer   | 页面、交互、编辑现场、加载/失败反馈    | SQL、文件操作、数据库连接、绕过 preload 直接访问主进程能力 |
| preload    | 暴露有限且有类型的业务 API             | 业务用例、任意 SQL 执行或任意路径读写                      |
| main / IPC | 生命周期、来源检查、请求分发和依赖装配 | 把全部业务逻辑堆进启动文件或 IPC 回调                      |
| services   | 协调一次业务操作、规则和事务边界       | Vue 响应式状态、窗口提示、终端输出                         |
| domain     | 核心类型与纯业务规则                   | Electron、Vue、数据库驱动和文件系统依赖                    |
| storage    | SQL、迁移、存储与文件操作              | 导入页面组件或决定用户交互流程                             |
| shared     | 真正跨进程共享的契约与错误结构         | 全局可变状态、数据库实例和杂乱工具集合                     |

禁止循环依赖和绕过约定的跨层导入。通过静态检查约束导入路径，同时审查桥接能力本身，不能仅靠目录名宣称实现了隔离。

服务通过明确的参数或装配后的依赖访问存储，业务代码不随处创建数据库连接。需要替换或隔离外部能力时引入小接口；不要求每个函数都配一个接口，也不引入通用依赖注入容器来解决尚未出现的问题。

公共模块只容纳已有的共同职责。两段代码外观相似但业务变化原因不同，不应强行抽成通用框架。不要用万能基类、通用 CRUD 服务或不断增加选项的超级组件掩盖不同规则。

## 5. TypeScript 与接口约定

- 开启 strict，禁止通过关闭类型检查解决实现问题。外部输入先视为 unknown，经运行时校验后再进入业务层。
- 避免 any、双重类型断言和无依据的非空断言。第三方类型缺失确需局部绕过时，缩小范围、写明原因并提供实际校验；不在整文件禁用检查。
- 不随意使用 `@ts-ignore` 或全局 eslint-disable。必要的预期类型错误应采用可检查的局部说明，不能为了让检查变绿掩盖错误。
- IPC 请求/响应通过 shared 中的契约统一；跨进程只传明确可序列化数据，不传连接、Vue 对象或随意暴露原始异常。
- 新字段明确默认值、空值语义与兼容行为。不要复制业务状态到多个字段再手动同步；手记分类以 `category` 为唯一来源，待办完成通过改分类实现，不再保存 `task_status`、`isTodo` 或 `isCompleted` 等副本字段。
- 接口变化时一起修改生产者、消费者和相关测试；向后兼容仅在有真实调用方或已有持久数据需要时设计，不保留永远不用的旧分支。
- 存储行、业务对象和页面展示数据在必要时映射，避免页面绑定数据库的每一个列名；映射也不应为每一层制造一份无差异类型。

## 6. 健壮性：正常路径和失败路径一起实现

- 输入验证覆盖正文空白、目标不存在、目标已删除、非法时间和无效状态等真实边界；UI 校验帮助体验，业务入口仍须校验。
- 区分可预期的业务失败与内部故障。错误应说明发生了什么、当前内容是否保存以及用户能做什么；不能将写入失败伪装成空列表或操作成功。
- 禁止空 catch、无解释地忽略 Promise、统一返回 true 掩盖失败。异步错误必须被处理或明确向上层传播。
- 资源生命周期明确：数据库连接、文件句柄、事件监听、定时器及工作线程在对应边界释放。重复打开页面不能累计监听器或写入任务。
- 对保存、关联等可能重复触发的动作采用幂等语义或稳定操作标识；按钮禁用只是 UI 辅助，不能替代存储约束。
- 草稿保存处理乱序请求与旧响应，不能让旧正文覆盖新输入；正式保存与草稿清理整体提交，失败保留编辑内容。
- 重试必须有明确条件和上限，不能对业务校验失败、永久错误或非幂等操作盲目循环重试。
- 进程退出、导航和取消操作有明确行为。长任务保持界面可响应；若不能安全取消，应明确反馈而非假装已经取消。
- 日志记录操作、错误码和必要上下文，避免整篇笔记、草稿、令牌或证书内容进入日志。开发调试不成为默认泄露个人知识的理由。

## 7. SQLite 与数据保护

用户知识是项目的核心资产，数据规则遵循需求和总纲，不靠 UI 习惯维持一致性。

1. SQLite 为结构化数据唯一主存储；正文与关系不在 JSON 文件或可变前端缓存中再建立另一套权威副本。
2. SQL 值使用参数绑定，动态排序等标识符使用白名单；每个连接显式启用外键，关联表以约束防止重复。
3. 同一业务操作涉及多表时，在同一数据库事务中执行，并在失败时正确回滚。不要将事务拆成数个互不关联的 IPC 请求。
4. 连接与写入调度集中管理，避免各模块持有独立无协调的写连接；事务保持短小，不在事务中等待用户交互或不受控的外部操作。
5. 删除与恢复遵守软删除规则。禁止为修复启动失败静默删库重建、丢弃无法解析的记录或未经说明自动清理用户数据。
6. 已发布迁移不重写，新增迁移包含版本前置条件与失败处理。模式变化需要验证已有数据库的升级路径；破坏性变化提供可恢复备份和明确数据转换。
7. 备份、恢复及附件文件操作遵循总纲的一致性流程；数据库事务不能自动回滚普通文件操作。完整备份必须实际恢复验证。
8. 测试和开发实验使用隔离数据目录，不能对真实知识库运行清库、压力测试或故障注入。
9. 代码回退不一定能回退数据结构；交付数据库变更时说明数据兼容范围与恢复方式，不承诺只回退代码就能恢复一切。

## 8. Vue 与 Electron 的具体要求

- Vue 组件围绕明确交互职责拆分；页面协调业务，复用组件通过 props/emits 等明确输入输出协作，不直接修改外部对象的内部状态。
- 派生数据优先计算得到，不复制到多份响应式状态。watch 用于确有必要的副作用，避免互相监听形成循环更新。
- 编辑现场、加载状态、成功与失败反馈分别表达；尚未持久化的数据不能显示已保存，失败后输入不能被刷新或导航静默清空。
- 主进程与渲染进程保持隔离，preload 暴露有限能力；IPC 校验来源及输入，不开放任意命令、任意 SQL 或任意文件访问。
- Markdown 渲染防止执行用户内容中的脚本，外部链接与路径按明确规则处理，不能为方便渲染关闭 Electron 安全边界。
- 文件路径由平台 API 派生，用户数据不放安装目录；驱动、worker、迁移与资源路径要在打包环境验证。
- 优化针对测量到的耗时或明确的阻塞风险。不能为了推测中的性能收益牺牲数据一致性或写成难以阅读的技巧代码。

## 9. 依赖、配置与可复现性

- 统一使用 pnpm 与锁文件，不混入其他包管理器锁文件。记录实际验证的 Node、包管理器和 Electron 版本。
- 添加依赖前检查是否已有合适能力，说明用途、维护成本和运行时影响；允许使用成熟库，不设“零依赖”指标，也不随手加入整套框架。
- 依赖升级针对本次需要，涉及 Electron、原生模块或构建工具时验证实际运行/打包；不只依靠类型检查通过。
- 禁止把本机绝对路径、用户目录、证书或秘密写入业务配置和源码。环境相关选项在明确位置集中管理。
- 临时调试开关不变成生产默认值。生成文件通过源配置重新生成，不手改构建产物掩盖问题。

## 10. 验证要求：证明行为，而非凑测试数量

| 修改类型               | 应提供的验证                                                            |
| ---------------------- | ----------------------------------------------------------------------- |
| 业务规则与缺陷修复     | 针对输入、预期行为和关键失败路径的测试；可稳定复现的缺陷增加回归用例    |
| SQL、关系、删除恢复    | 临时真实 SQLite 集成测试，验证约束、查询及失败回滚                      |
| 模式迁移、备份恢复     | 旧版样例升级或真实备份恢复，对比内容与关系，验证损坏/不兼容输入         |
| 界面与交互             | 相关组件或流程验证，加实际运行检查；关键草稿/保存流程有必要的自动化覆盖 |
| Electron、驱动与打包   | 验证相应运行环境和安装包；跨平台声明需对应平台证据                      |
| 文档、注释或低影响样式 | 对应内容/链接/视觉检查，无须为可逆的简单改动编写无意义测试              |

测试观察公开行为和不变量，避免仅断言实现调用次数、照抄实现算法或大量快照代替行为判断。时间、随机 ID、临时路径等需要可控制的测试入口，但不为了 mock 把简单代码拆成框架。

不能通过删测试、放宽断言、跳过失败用例或关闭检查来掩盖回归。规范确实变化时，说明变化依据并同步调整行为与测试。测试只能证明覆盖到的场景，不能替代代码审查或真实体验。

代码变更执行仓库实际配置的类型检查、lint、格式检查、相关测试，以及受到影响的构建/桌面验证。先做针对性检查，根据影响范围扩大；无新改动或失败原因时不反复跑无关测试。

无法运行某项检查时，区分“未运行”“运行失败”“通过”，写明原因及未验证影响。尚未创建工程时不虚构检查脚本和测试结果；文档链接检查不等于应用功能通过。

## 11. 跨会话工作流程与改动保护

### 开始前

阅读根目录 项目协作指南.md、本文和与任务相关的当前需求/结构说明，再阅读将修改的核心代码、调用方与测试。检查工作区现状；已有 Git 时查看当前分支、未提交差异和必要历史，不能假设所有未提交内容都是自己生成的。

#### 文档规范

分阶段功能实现必须在每阶段开工前准备任务书与设计文档，完成后补充交付文档。所有功能文档遵循以下规范：

**目录结构**：

- 基础文档：`docs/foundation/` - 项目级别基础规范（产品规格、开发准则、技术栈等）
- 功能文档：`docs/features/{模块}/` - 按功能模块分组（note-taking、topic-induction、ai 等）
- 版本文档：`docs/releases/{版本}/` - 版本里程碑与阶段交付总结
- 决策记录：`docs/decisions/` - 重要架构与技术决策

**命名规范**：

- 任务书：`{YYYY-MM}-{功能简称}-任务书.md`
- 设计文档：`{YYYY-MM}-{功能简称}-设计.md`
- 交付文档：`{YYYY-MM}-{功能简称}-交付.md`
- Bug 修复：`{YYYY-MM}-{问题简述}-修复.md`
- 方案文档（未实施）：`{YYYY-MM}-{功能简称}-方案.md`

**Frontmatter 要求**（每个文档开头）：

```yaml
---
created: YYYY-MM-DD
completed: YYYY-MM-DD # 交付文档必填
status: planned | in-progress | delivered
feature: 功能模块英文名
related:
  - 相关文档相对路径
---
```

**任务书内容**：目标、范围、验收标准、不包含的内容；不写实现细节，关注用户可见效果。

**设计文档内容**：架构方案、契约定义、存储设计、关键流程、失败路径、兼容性处理、测试计划。

**交付文档内容**：实现内容、关键变更、实际验证结果、已知限制、后续建议；同步实际结果，不以总规划替代实际交付。

**文档链接**：任务书、设计、交付三联文档通过 frontmatter 中的 `related` 字段互相链接；文档间引用使用相对路径。

以简短说明明确本次改什么、为什么、如何验证。对现有实现有疑问先查证，不依靠上一会话的记忆或文档标题推断实际代码已经存在。

### 修改中

- 保留用户与其他会话的未提交工作，不以 reset、checkout、清理脚本或覆盖整个文件的方式抹掉无关变更。整文件重写只有在目标确实需要且已理解现有内容时采用。
- 共享契约变更同时处理调用方；并行工作明确文件写入范围，避免多个代理互相覆盖。
- 功能实现、结构重构、依赖升级和纯格式修改尽量分开，便于理解、定位回归与回退；不要求为了凑提交数量切碎一个不可分的修复。
- 发现文档与实现冲突时，对照当前用户要求判断；修正规范与实现，不通过默默改验收条件让错误实现显得正确。
- 重要决策在 docs/decisions 留简短记录：问题、选择、原因、代价与重新评估条件。局部命名和普通文件拆分不需要专门写决策文档。

### 交付前

主代理或负责人阅读最终差异，核对产品约定、依赖方向、失败路径、数据保护及验证结果。交付说明包含：改变的行为、关键文件、实际检查结果、剩余限制和必要的兼容说明。未完成部分明确标明，不写“全部完成”掩盖待验证项。

后续会话应能从当前文档、代码、测试与简明交付中继续工作，不能依赖只有某段聊天才知道的关键规则。

## 12. 子代理委派

- 大型文件处理、跨目录调查、独立验证或拆分实现适合并行时，可自主委派，无需额外确认；直接处理更快时由主代理完成。
- 基础文档、即将修改的核心代码与最终设计决策必须由主代理直接阅读和裁决，不能全盘外包。
- 子任务明确输入、输出、写入范围及验收标准；优先分配不阻塞主线的工作。主代理核验结论与最终代码，不直接把未核验输出作为交付。
- 任务停滞先检查状态，再缩小范围、停止或重新委派；结束后按工具能力结束任务或停止不再需要的运行，不让闲置代理继续修改文件。

## 13. 完成标准与规则演进

一次代码修改只有在以下问题得到清楚回答后，才能作为已完成交付：

- 行为符合当前需求吗，是否引入了未要求的新功能或约束？
- 命名、流程、注释足以让后来者理解吗？
- 依赖边界是否仍然成立，业务规则是否只有明确来源？
- 无效输入、重复操作与关键失败路径得到处理了吗？
- 用户数据、未提交改动和已有兼容性得到了保护吗？
- 与影响范围相符的验证是否完成，未验证部分是否如实列明？
- 文档、接口、迁移与实际实现是否保持一致？

这些原则通过严格类型、lint 导入限制、自动化测试、审阅和交付说明共同执行。文档本身不能保证没有缺陷，不能把“已阅读准则”当成质量证明。

首轮工程已提供类型、lint、格式、单元/真实 SQLite 与桌面测试入口；具体命令见 README。当前未接入 CI，检查需实际运行。检查规则逐步完善，不将未实现的门禁描述为已经生效。

准则可随项目经验修订，但不能为了绕过本次错误而弱化保护。若已有用户指令明确改变约定，执行并同步记录；若尚无授权且涉及需求、架构或数据处置的实质改变，先给出具体影响供用户决定。普通实现取舍不需要额外审批。
