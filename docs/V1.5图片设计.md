# V1.5 设计 · 手记附带图片

> 范围决定：手记为本地图片提供「选择文件」与「粘贴剪贴板图片」两种入口，图片作为手记的独立图集存在，不嵌入 Markdown 正文；每张图片可单独命名、可在手记详情中放大查看。删除沿用软删除。
> 本文是 V1.5 的实现依据，行为验收并入 [界面与交互基准](界面与交互基准.md)，数据边界以 [架构与实施](架构与实施.md) 为准。

## 1. 为什么图片必须和备份一起做

[产品规格](产品规格.md) 第 9.2 节要求：一旦存在受管理附件，备份恢复必须覆盖它们；[架构与实施](架构与实施.md) 第 4 节要求备份实现从开始支持附件目录。V1.5 一旦允许写入图片，磁盘上就会出现数据库快照覆盖不到的资产。若只把数据库恢复到干净目录，图片会全部变成断链而且不会报错——这是静默的数据丢失。

因此 V1.5 的范围包含**附件目录的备份与恢复**，但**不包含** V2 的完整备份界面：本轮提供的能力是「快照 + 附件目录」的一致目录包与恢复到空目录，活动库替换、暂停写入与启动检测仍留在 V2 阶段 5。这是有意的收敛，不是遗漏。

## 2. 产品行为

| 项目     | 规则                                                                                      |
| -------- | ----------------------------------------------------------------------------------------- |
| 归属     | 一张图片属于且仅属于一条已保存手记；不支持跨手记复用同一文件                              |
| 入口     | 手记详情的「添加图片」按钮打开系统文件选择；在详情内粘贴剪贴板图片直接加入                |
| 正文关系 | 图片不进入 Markdown 正文，不写引用语法；正文预览行为不变                                  |
| 命名     | 每张图片有独立显示名称，可为空；为空时展示原文件名，再为空时展示序号                      |
| 查看     | 详情中的缩略图可点击放大查看；放大层支持键盘关闭并遵循浮层焦点规则                        |
| 排序     | 按加入顺序展示，不做手动排序；位置取当前最大值加一，不复用已删除记录的位置                |
| 删除     | 软删除，图片行标记删除时间，文件保留；不提供物理删除与自动清理                            |
| 首页     | 先保存手记再加入图片；首页草稿阶段明确提示，不写入无法归属的图片                          |
| 搜索     | 图片名称不参与搜索；V1.5 不新增图片搜索                                                   |
| 限制     | 单图不超过 20 MB，单条手记不超过 50 张、累计不超过 200 MB；超出明确拒绝并保留已添加的图片 |

首页不提供图片入口的理由：图片必须挂在已存在的手记上，否则会产生无法归属的记录行；把图片先放在内存里等提交，会在异常退出时无提示地丢掉用户刚选的图。两者都比「先保存再加入图片」更差。

## 3. 数据模型

新增迁移 `migrations/002_note_images.sql`：

```text
note_images
  id            TEXT PRIMARY KEY      -- 客户端生成的稳定 UUID
  note_id       TEXT NOT NULL REFERENCES notes(id)
  relative_path TEXT NOT NULL UNIQUE  -- 相对数据目录，固定 attachments/<uuid>.<ext>
  mime_type     TEXT NOT NULL         -- 由文件签名判定，不接受调用方声明
  byte_size     INTEGER NOT NULL CHECK (byte_size > 0)
  width         INTEGER NOT NULL CHECK (width > 0)
  height        INTEGER NOT NULL CHECK (height > 0)
  display_name  TEXT NOT NULL DEFAULT ''
  original_name TEXT NOT NULL DEFAULT ''
  position      INTEGER NOT NULL CHECK (position >= 0)
  created_at    TEXT NOT NULL
  deleted_at    TEXT
  UNIQUE (note_id, position)
```

- `relative_path` 用 CHECK 约束限定必须以 `attachments/` 开头且不含 `..`，让数据库本身拒绝逃逸路径。
- 外键指向 `notes(id)`：图片只能挂在已存在的手记上，孤儿行无法写入。
- 不建立 `attachments` 通用表。当前只有图片一种附件，字段按图片定义；将来真出现其他类型时再通过新迁移引入，不预先抽象。
- 图片行不参与手记的 `revision` 计数。手记正文的并发保护与图集变更互不干扰，避免「只加了一张图」把正在编辑的正文判成冲突。

## 4. 文件存储与一致性

文件位于 `<数据目录>/attachments/`，扁平存放，文件名即图片 ID 加扩展名。扩展名由文件签名推导，不由调用方提供——即使原文件名带可执行后缀，落盘也只可能是图片扩展名。

写入顺序与失败处理：

1. 校验字节数、逐张判定文件签名，取不到受支持签名则拒绝；
2. 用稳定 ID 写入附件目录；
3. 在事务中插入图片行；
4. 第 3 步失败时删除刚写入的文件。

已知限制：第 4 步的删除本身也可能失败，此时会留下一个不可见的孤儿文件。V1.5 不做自动清理——自动清理正是开发准则禁止的「未经说明清理用户数据」。孤儿文件会随备份一起被复制，占用可忽略，处理策略留给 V2 的回收站阶段重新评估。

读取路径（自定义协议）每次请求都做完整校验：ID 必须是合法 UUID → 图片行存在且未删除 → 所属手记存在且未删除 → 路径落在附件目录内。渲染端无法通过构造 URL 读取任意文件。

## 5. 备份与恢复

沿用现有 `restoreDatabaseBackup` 的「恢复到空目录」语义，扩展为：

- `backupDatabaseSnapshot(destination)`：先备份数据库，再复制附件目录，最后写入清单文件 `backup.json`，包含格式版本、模式版本、创建时间、数据库文件名、附件文件数量与每个附件的校验值。复制失败或校验不一致时删除本次临时结果，不留下半套备份。
- `restoreDatabaseBackup(source, target, migrations)`：接受数据库文件或包含清单的目录包。目录包先校验清单与附件校验值，再把数据库与附件一起恢复到目标目录；目标目录必须为空。旧版本的裸数据库文件继续支持，并按「无附件」处理。
- 校验值使用 `node:crypto` 的 SHA-256，并同时核对字节数。
- 恢复在清单校验全部通过后才创建目标目录，因此被拒绝的恢复不会在磁盘上留下任何痕迹。

V1.5 备份是目录包，不压缩、不加密。压缩格式、增量与保留策略留给 V2。

## 6. 跨层契约

`src/shared/contracts.ts` 新增图片能力，渲染端只拿到元数据与相对路径，不接触文件系统：

| 方法                                   | 说明                                                 |
| -------------------------------------- | ---------------------------------------------------- |
| `loadImages(noteId)`                   | 读取该手记的有效图片列表                             |
| `addImagesFromDialog(noteId)`          | 主进程打开系统文件选择并复制所选图片；取消返回空结果 |
| `addImageFromClipboard(noteId, image)` | 保存剪贴板位图；载荷含 MIME、字节数组与原始名称      |
| `renameImage(imageId, displayName)`    | 修改显示名称                                         |
| `deleteImage(imageId)`                 | 软删除                                               |
| `openImageDialog()`                    | 备份/导出等需要选择目标目录时使用（V1.5 仅内部预留） |

图片通过自定义协议 `memocraft-image://image/<id>` 展示。该协议注册为 `standard` 且 `secure`，渲染端 `index.html` 的 CSP 已把 `memocraft-image:` 加入 `img-src`。

访问控制按图片 ID 在存储层完成（记录未删除、所属手记未删除、路径仍在附件目录内），渲染端无法凭 URL 读取任意文件。协议只注册在本窗口所属会话上，不按来源做白名单：开发模式界面来自 `http://localhost`、打包后来自 `file://`，按来源限定会误伤开发环境。

## 7. 界面

- 手记详情（`NoteDrawer.vue`）在正文之后新增图集区：空状态说明可用「添加图片」或直接粘贴；有图时展示缩略图网格，每张下方是可编辑的名称输入框与删除按钮。
- 缩略图使用固定宽高比的容器，加载失败显示明确占位，不出现破图。
- 点击缩略图打开放大层：居中显示原始比例，最大不超过视口；提供关闭按钮与 `Esc`；遵循 `useModalFocus` 的焦点范围与来源恢复。
- 「添加图片」在保存进行中或手记尚未保存时禁用，并给出原因。
- 键盘与无障碍：缩略图是可聚焦的按钮并带可读名称；名称输入框有独立标注；放大层是 `role="dialog"` 模态浮层。
- 动效沿用现有三档时长与缓动；减少动态偏好下不播放位移与缩放。

## 8. 验证要求

| 层次     | 用例                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------ |
| 单元     | 显示名称规则、文件签名识别、扩展名推导、字节上限与数量上限校验、路径逃逸拒绝                                 |
| 集成     | 真实 SQLite：写入与读取图片、位置唯一约束、外键拒绝孤儿、软删除后不可见、删除手记后图片隐藏、路径 CHECK 生效 |
| 备份恢复 | 目录包恢复后数据库与附件逐项一致；清单校验失败时拒绝恢复且不改动目标目录；裸数据库文件仍可恢复               |
| 桌面     | 详情内添加图片、重命名、放大查看、删除；粘贴路径以合成 `ClipboardEvent` 覆盖                                 |
| 实际运行 | 用真实截图文件走一次选择、粘贴、放大、重启后仍可见，并核对附件目录与数据库记录一致                           |

图片解码需要真实图片字节，测试样例用代码在临时目录生成最小 PNG/JPEG，不向仓库提交二进制样例。

## 9. 明确不做

- 图片嵌入 Markdown 正文、拖拽排序、跨手记复用、图片搜索、OCR、压缩与格式转换。
- 附件上传以外的通用文件类型界面。
- 物理删除与自动清理孤儿文件。
- 活动库替换式恢复、备份压缩包与增量备份。
