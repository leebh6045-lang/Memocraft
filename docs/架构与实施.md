# Memocraft 架构与实施 · v1

> 当前开发规范。项目已进入首轮桌面实现；本文的完整 v1 目标不等于全部已完成。实际范围与验证见 [首轮交付](首轮交付.md)。

## 1. 当前基线

产品行为以 [产品规格](产品规格.md) 为准；结构与质量要求分别见 [项目结构](项目结构.md) 和 [开发准则](开发准则.md)。当前明确的产品决定优先于旧约定，变更时同步维护受影响规范。

当前基线：Electron + Vue 3 + TypeScript 桌面版；四模块是首页、随手记、知识归纳、长期事务；SQLite 为唯一结构化主存储。手记使用“收获、待办、完成、杂项”单一分类，不另建收件箱或任务状态。CLI 不作为前置产品。开发阶段应用左下角显示“内测中”。

## 2. 架构与项目结构

```text
Vue 页面与组件
    ↓ preload 暴露的有限业务 API
主进程 IPC 适配与业务调度
    ↓ 可测试的业务服务
受控存储层（必要时使用工作线程或独立进程）
    ↓
SQLite + 附件目录
```

完整文件树与目录职责统一放在 [项目结构](项目结构.md)，包含根目录配置、四模块页面、业务与存储分层、迁移、测试、打包资源及用户数据路径。

首版采用单个 package.json，按职责组织源码；按实际功能逐步创建文件，不预先建立多包工程或空壳业务层。公开规范统一放在 docs 中。

渲染进程不持有文件系统、数据库连接或通用 SQL 执行权限。业务服务负责运行时校验，不能仅依赖 TS 类型；SQL 使用绑定参数，排序字段等用白名单。界面收到持久化成功后才能显示已保存。

单个应用实例统一管理当前数据目录，写入经过统一队列。一项完整业务操作使用一个数据库事务。同步驱动的重查询、备份等放在工作线程或进程执行，避免堵住窗口响应；具体方案由最小运行与打包样例决定。

## 3. 数据模型方向

下面是落库设计基线；完整 DDL 通过迁移管理。手记、草稿、图片、归纳与收录关系已落地（`001`–`003`），事务、动态、两类引用与动态标签已落地（`004`）。实体使用稳定、全局唯一的 ID，标题不作为键。数据库列采用 snake_case，应用类型可用 camelCase，由存储层映射。

| 表                         | 主要内容与约束                                                                                              |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `note_drafts`              | 首页草稿：稳定 ID、唯一画布槽位、草稿载荷、递增 revision、更新时间；载荷可含尚未正式保存的内容与待关联 ID   |
| `notes`                    | ID、正文、可空标题、非空 category、创建/修改时间、软删除时间；category 仅允许四个固定值                     |
| `topics`                   | ID、标题、说明、创建/修改时间、软删除时间                                                                   |
| `threads`                  | ID、标题、说明、当前概况、进行中/已归档、创建/修改时间、软删除时间                                          |
| `thread_entries`           | ID、非空 thread_id、发生时间、描述、正文、创建/修改时间、软删除时间                                         |
| `note_topics`              | note_id + topic_id 联合唯一，表达收录                                                                       |
| `entry_notes`              | entry_id + note_id 联合唯一，表达动态引用                                                                   |
| `thread_notes`             | thread_id + note_id 联合唯一，表达事务直接引用                                                              |
| `tags`                     | ID、显示名称及去重用规范值                                                                                  |
| `note_tags` / `entry_tags` | 分别关联手记、动态与标签，同一配对唯一                                                                      |
| 迁移元数据                 | 记录当前 schema_version 与已执行迁移                                                                        |
| `note_images`              | 手记图片：ID、非空 note_id、受约束的相对路径、类型、字节数、宽高、显示名称、原文件名、位置、创建/软删除时间 |

首页是页面模块，不需要创建 `homes` 知识表；首页编辑恢复由 `note_drafts` 支持。草稿载荷中的 JSON 只是库内一个字段，不是第二份正文主存储。提交时重新验证待关联目标是否存在且未删除。

### 3.1 单一手记分类

`notes.category` 是分类与完成语义的唯一来源，NOT NULL，DEFAULT 'insight'，由 CHECK 约束限定以下值。名称和排列顺序由共享契约中的显式映射定义，不按字符串字母顺序排列。

| 顺序 | category          | 界面名称 |
| ---- | ----------------- | -------- |
| 1    | `insight`（默认） | 收获     |
| 2    | `todo`            | 待办     |
| 3    | `done`            | 完成     |
| 4    | `misc`            | 杂项     |

新建草稿预选 insight；自动保存和恢复同时保留正文及所选 category。所有创建入口使用相同默认值和校验规则，非法值拒绝写入。正式保存后下一条新草稿重新预选 insight。

改选只更新 category 和修改时间。todo 与 done 可相互改选，也允许直接创建或改选任意一类；不会删除、复制正文或改变收录/引用。全部查询只过滤软删除，分类查询叠加 category 等值条件。

不再建立可自定义的 categories 表、category_id 或独立 task_status / isTodo / isCompleted 字段；不存在“分类为收获但同时已完成”的双重状态。整理进度、问题进度、回顾标记与已取消状态同样不进入模型。标签保持独立且自由，不反向改变分类。

当前尚无正式数据库，因此初始迁移直接采用四类设计，不生成针对不存在旧库的迁移。若未来导入早期试验数据，须先制定可验证的分类映射和备份恢复方案，不能静默丢弃旧值。

### 3.2 关系唯一来源与查询

归纳、动态、事务的关联各只存于对应关联表。不在实体中再维护可写的 homeId 或 noteIds 数组。详情查询可以生成关联数组，用于传给界面，但不能成为另一份持久化事实来源。

每个连接显式启用并检查外键。动态的 thread_id 非空且有外键，关系两端有外键；关联表联合主键或唯一约束阻止重复。普通操作关联前也检查软删除状态，外键不能代替这项业务规则。

标题允许重复，通过 ID 寻址。创建/修改时间存储统一 UTC 格式，界面以本地时区展示。发生时间经明确的本地时区解释后转换保存；空值用当前时间，非法时间拒绝。时间线使用发生时间、创建时间、ID 稳定排序。

### 3.3 草稿转手记

同一首页草稿拥有稳定 ID，可作为正式手记 ID 和重复提交的识别键。处理乱序自动保存请求时校验 revision，避免旧内容覆盖新内容。

正式保存时暂停该草稿的自动保存队列，提交最新正文与 revision。在一个事务中创建手记、建立所选关系、移除对应草稿；提交成功才清理编辑器并开始新草稿。重试已成功的同一 ID 返回原结果，不能新建另一条。过期的自动保存不能在正式提交后把旧草稿重新创建出来。

清空首页内容应同时清除已保存的旧草稿，防止重启后旧内容复活；空白编辑区不创建正式手记。已有手记的编辑现场独立于首页新建草稿，不共用可覆盖的持久化槽位。普通编辑和草稿写入失败均保留内存中的最新内容并提示。

### 3.4 删除与恢复

删除使用 deleted_at，不做物理级联删除。归纳删除后关系保留、常规查询隐藏；手记本身不变。手记删除后引用端保留占位提示，恢复可重新显示。

删除事务只设置事务的 deleted_at，其动态是否有效取决于自身及父事务均未删除。恢复事务不会清除动态自己原有的 deleted_at，因此不会误恢复此前单独删除的动态。
可见性谓词集中实现在 `src/storage/visibility.ts`：实体自身未删除、动态额外要求父事务未删除、图片额外要求所属手记未删除；其余查询从这里拼接，不再各写一份判断。删除与恢复的界面入口见 [界面与交互基准](界面与交互基准.md) 与 [阶段 4 交付](阶段4交付.md)。归档 status 独立，不在恢复事务时偷偷改回进行中。

删除/恢复动态时检查父事务状态；父事务被删除时先恢复父事务。首版不提供永久清空功能，不引入多份关系快照来实现恢复。

## 4. SQLite、正文与文件

```text
应用用户数据目录/
  data/
    memocraft.sqlite
    attachments/
```

数据库目录由 Electron 的用户数据路径派生，不写进安装包或代码仓库。升级程序时不覆盖该目录。SQLite 使用 WAL 时可能出现 `memocraft.sqlite-wal` 和 `memocraft.sqlite-shm`；它们由数据库引擎管理，不由清理脚本随意删除。

### 4.1 手记图片（V1.5）

图片元数据在 `note_images` 表中，文件平铺存放在 `attachments/`，文件名是图片 ID 加由签名推导的扩展名。要点：

- `relative_path` 由 CHECK 约束限定必须以 `attachments/` 开头且不含 `..`，数据库本身拒绝逃逸路径；外键指向 `notes(id)`，未保存的手记无法挂上图片。
- 写入顺序是「校验签名与尺寸 → 写文件 → 事务插行」，插行失败时补偿删除刚写的文件。文件系统没有事务，因此不声称 SQL 回滚能撤销文件写入。
- 软删除沿用 `deleted_at`：删除图片只标记时间，文件保留，因此路径唯一约束长期有效；新增图片的位置取当前最大位置加一，不复用已删除记录的位置。
- 渲染端通过自定义协议 `memocraft-image://image/<id>` 取图。协议只接受图片 ID，并按「ID 合法 → 记录未删除 → 所属手记未删除 → 路径仍在附件目录内」逐项校验；渲染端无法凭 URL 读取任意文件。协议在应用就绪前以 `standard` 与 `secure` 登记，`index.html` 的 CSP 在 `img-src` 中放行该来源。
- 图片不使用手记的 `revision`：只改图集不会把正在编辑的正文判成冲突。

### 4.2 备份与恢复（V1.5）

备份是目录包：数据库快照、`attachments/` 与 `backup.json` 清单（格式版本、模式版本、创建时间、数据库文件名、每个附件的相对路径与 SHA-256）。顺序为「快照 → 复制附件 → 写清单 → 逐项校验 → 目录改名发布」；任一步失败都删除临时目录，不覆盖已有备份。

恢复接受目录包或早期的裸数据库快照。目录包先校验清单与每个附件的校验值，全部通过后才创建目标目录，再在临时目录内完成迁移与内容校验，最后把附件与数据库一起发布；被拒绝的恢复不在磁盘上留下任何痕迹。

活动库替换式恢复已实现：关库排空写入 → 把当前数据整体复制成恢复前备份并写下进行中标记 → 整体替换 → 重新打开并校验 → 提交或回滚。启动时检测进行中标记，发现未完成的恢复先回滚再打开；标记在而备份缺失则拒绝启动。备份、导出与恢复暂存都在存储线程执行并按操作使用长超时，替换由主进程在数据库关闭后完成。

正文统一以 Markdown 文本保存在库中，附件路径相对于 data 目录。数据库、缓存、用户附件与本机备份不提交代码 Git 仓库。

数据库事务不能自动覆盖普通附件文件操作。图片写入遵循「先写文件、再事务插行、失败补偿删除」的顺序，并通过失败测试验证；不声称 SQL 回滚能撤销文件写入。

数据库驱动由实际 Electron 运行时决定，不能用开发机 Node 的版本替代验证。SQLite 可以是正式长期主库，SQLite 为正式本地数据库，无需独立数据库服务。

## 5. 搜索设计

AI 扩展采用主进程配置/调用服务、有限 preload 接口和现有存储线程，详见 [AI 阶段一设计](features/ai/2026-10-AI接入-设计.md)。版本 `006` 新增 `ai_settings` 模型配置；机器绑定的密钥经系统加密保存在知识库目录之外，不进入知识库备份和导出。网络调用不占用 SQLite 事务。[阶段二归纳建议](features/ai/2026-10-AI归纳建议-设计.md) 通过独立服务复用配置快照、既有归纳查询和标签池，严格校验输出后只返回提示；采纳标签仍沿用草稿保存链路，不增加迁移或缓存。Flash 通过独立 `AiImageReader` 纳入有限草稿图片，Pro 按文字生成并提示视觉能力限制；图片统计由本地计算，字节不经过渲染端。关闭与恢复暂停 AI 入口并等待请求结算。阶段四新增 `007` 周期总结缓存，服务复用图片 reader 与取消接替链，结果写入 SQLite 并随知识库备份恢复。日期工具统一自然周/月和本地零时的 UTC 半开区间，待办龄期与归纳收录数由数据库计算。此接入不改变下述本地关键词搜索行为。

首版从 SQLite 查询匹配内容，覆盖需求规定的全部对象与字段；已归档事务可搜，草稿、软删除内容及被删除父事务的动态不在普通结果中。

使用参数化子串匹配，明确转义 LIKE 的百分号、下划线等通配符，使用户输入按文字搜索。中文连续原文可匹配；首版英文字母大小写不敏感，不声称 SQLite 默认实现所有语言的大小写折叠。

为关联外键、事务动态时间排序等常用查询设置必要索引。全文索引与中文分词依据数据量、查询计划与真实搜索体验另行选择；不假设开启 FTS5 就自动具备合适的中文分词。

V2 阶段 3 已按真实规模测量：2000 条手记、200 个归纳、100 个事务与 3000 条动态下，罕见词、跨类型常见词与空查询都在 1–2 ms 量级（`tests/integration/search-scale.test.ts`），因此首版保持参数化子串匹配，不引入全文索引；数据量显著增长或出现可感知延迟时重新测量。

## 6. 备份、恢复与迁移

建议完整备份包含数据库快照、attachments 目录和带版本/校验信息的 manifest；具体采用目录包或压缩包在备份里程碑固定，不把未经实现的格式描述成既有接口。

备份时协调写入队列与附件变更，使用经过验证的 SQLite 备份 API 生成一致快照，再复制同一状态的附件，校验完成后标记成功。不可只复制正在使用中的主库文件；失败不覆盖已有有效备份。

恢复先在临时目录校验数据库完整性、外键、备份版本及附件路径/校验值；不允许包内路径逃逸到目标目录之外。用户确认恢复后，先暂停新编辑及新的数据变更，处理已有待保存请求并排空写入队列，再生成当前数据备份；保存或备份失败则停止恢复，保留原数据与尚未保存的内容。保持暂停状态，关闭连接并替换活动数据，避免备份后又产生未受保护的新写入。恢复阶段记录足够的进度用于失败回滚和中断后恢复；启动时检测未完成恢复，不能直接把半套数据当成正常库打开。

恢复只做整库替换，不合并两份库。过新的未知格式拒绝覆盖；支持的旧版本在副本上迁移并验证。迁移按版本顺序执行，成功后才更新模式版本；禁止失败时静默删库重建。

可读导出生成 Markdown 文件、元数据和关联清单，文件名包含稳定 ID 防止同名覆盖，并处理 Windows 非法路径字符。可读导出服务迁出与独立阅读；完整恢复使用完整备份格式。备份成功不等于恢复验收完成，必须实际恢复并比较。

## 8. 验证与工程习惯

统一执行 [开发准则](开发准则.md)；工程初始化时将类型检查、lint 边界、格式与测试规则落实为实际脚本，交付不得仅以“已阅读规范”代替验证。

- domain/services：四类合法值及默认值、分类改选、固定顺序、关联幂等、空内容保护与明确错误。
- storage：用临时真实 SQLite 数据库验证外键、唯一约束、事务回滚、查询、软删除、迁移与恢复；不只 mock SQL 返回值。
- desktop：首页草稿切换、失败保留、保存反馈、双击防重复、三类创建入口与全手记默认列表。
- 数据保护：人为制造写入/恢复失败、损坏备份和版本不兼容，验证现有数据仍可恢复。
- 跨平台：安装包内驱动、用户数据路径、Markdown/导出文件名、备份选择与恢复；声明支持的架构需有实际证据。
- 日常质量：类型检查、lint、格式检查、针对性测试和构建各自通过；只写对行为或风险有价值的测试。

初始脚本名称与目录最终以脚手架实际配置为准，建立后写进项目 README；这里不提供尚未存在就声称可运行的命令。关键取舍用简短决策记录解释原因，不以零依赖、固定文件数或无限预留抽象作为代码质量指标。
