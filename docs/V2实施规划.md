# Memocraft V2 实施规划

> 本文是 V2 阶段的实施路线与验收依据。**界面效果与控件互动以第 3 节的设计基准为准**，产品行为以 [产品规格](产品规格.md) 为准，分层与质量要求见 [开发准则](开发准则.md) 与 [项目结构](项目结构.md)。
> [V2 阶段规划](V2阶段规划.md) 保留用于追溯当时的判断；本文取代其中的阶段安排与基线描述，冲突时以本文为准。

## 1. 范围与推进方式

V2 等于补完 [产品规格](产品规格.md) 已定义、首轮与 V1.5 未交付的剩余范围：知识归纳、长期事务与动态、全对象搜索、回收站、完整备份恢复、可读导出、平台与发行。**不新增规格外功能。**

推进方式（本轮确定）：

1. 每个阶段独立交付、独立验收，**验收通过后才进入下一阶段**；每阶段交付说明必须如实区分「通过 / 失败 / 未运行」。
2. 阶段 1 在 `607faf2` 上**从零重写**，不采用此前被回滚的实现代码（依据见第 5 节）。
3. 界面一律按第 3 节的设计基准实现，不自由发挥；基准未覆盖的界面（回收站页面、备份恢复导出入口、设置）先补设计再实现。

## 3. 界面与交互基准（方案 D · 流畅）

基准物是原型 `方案 D`（原型目录里编号 `04-flow.html`，本地副本 `.local/flow.html`）。两点必须知道：

- 本地副本的 `assets/` 相对路径已失效，直接打开是无样式空壳；可运行副本由 `flow.html` 与 `.local/prototypes/assets/{proto.css,core.js,proto.js}` 组合而成。需要对照时按此组合打开。
- `.local` 不提交（[仓库内容政策](仓库内容政策.md)），因此**规范正文写在本节**，实现与验收都以本节为准；本地原型仅作对照素材，不作为公开必读。

### 3.1 基准地位与裁决口径

基准物是原型「方案 D · 流畅」（原型目录编号 `04-flow.html`，本地副本 `.local/flow.html`）。本地副本的 `assets/` 相对路径已失效，直接打开是无样式空壳；需要对照时用 `flow.html` 搭配 `.local/prototypes/assets/{proto.css,core.js,proto.js}` 组合出可运行副本。`.local` 不提交（[仓库内容政策](仓库内容政策.md)），因此**界面规范正文写在 [界面与交互基准](界面与交互基准.md)**（设计令牌、布局、控件、页面结构、按键、动效、无障碍条款），本地原型仅作对照素材，不作为公开必读。

裁决口径（2026-09-22 确定）：**视觉、布局、控件互动与文案以原型为准；数据保护、无障碍、失败路径与持久化条款保留既有要求**，不因原型未体现而降低。据此已完成的收口：

- [界面与交互基准](界面与交互基准.md) 已按此口径改写，并写明两处对原型的刻意收紧：手记卡片标题两行截断、主题切换先锁定旧样式且偏好持久化。
- 原型缺失但必须保留的能力：焦点陷阱与归还、`aria-modal`、输入法合成期保护、真实持久化与失败保留、防重复提交、图片图集、搜索的加载 / 失败 / 空结果三分表达。
- 原型中的死代码（未被自身使用的小型选择器样式、紧凑卡片分支、未调用的导出函数）不作为实现依据。
- 原型桩数据用 `gain` 表示「收获」，应用与已发布迁移用 `insight`；界面文案一致，**以 `insight` 为准**，不为此新增迁移。

### 3.2 基准未覆盖的三块界面（已出稿并确认）

回收站页面与恢复入口、备份 / 恢复 / 导出的入口与进度反馈、设置，原型都没有画。设计稿见本地原型 `10-v2-gaps.html`（不提交），结论已写入 [界面与交互基准](界面与交互基准.md) 第 3 节：回收站与设置都是左下角「内测中」右侧的图标入口（侧栏工具区保持搜索、专注模式、主题三项），设置快捷键 `⌘,`，分外观 / 数据 / 关于三区；主题提供浅色 / 深色 / 跟随系统三选，侧栏按钮保留快速切换；备份、恢复、导出集中在设置的数据区，恢复用模态确认并写明影响范围与不可取消。

### 3.3 施工差异清单（相对当前 `main`）

现有 `src/renderer/src/assets/theme.css` 本身已是基准样式的移植版，令牌、按钮、卡片、抽屉、搜索浮层与多数动效已逐条对应。**差距主要在交互与缺失页面上，不在视觉重做。** 逐项差异已核实如下，作为阶段 1 的施工清单。

**A. 基准有、应用没有（V2 要补）**

- 结构：知识归纳与长期事务两套页面（现为占位页）；通用对话框（新建归纳/事务、选择器、删除确认）及其多选列表；面包屑、概况框、时间线、引用 chip、集合卡片序号、状态胶囊、归档态卡片、卡片「移出」按钮；搜索的四类结果分组。
- 交互：软删除 + 提示条撤销机制（基准中 8 处触发点）；提示条携带操作按钮；列表重排 FLIP（应用现为 `TransitionGroup` 位移）；列表→详情的视图过渡；空正文保存的抖动；分类与标签的 chip 选择行；首页「补充」按钮的条目计数。
- 视觉：卡片脚注的关系上下文（`收录于 X`、`被引用 N 处`）；搜索结果的命中高亮与单行上下文；最近手记的时间格式（「今天 10:24」）；断点（统一为 1000–1050 / 900 / 720 三档，应用现为 1050/800）。

**B. 应用有、基准没有（必须保留，不得为了对齐而退化）**

- 真实持久化、保存失败保留输入、版本冲突与重试、关闭窗口守卫、加载与失败视图、常驻状态条。
- 焦点陷阱、`inert` 隔离、`aria-modal` 与焦点归还——基准没有，但这是既有能力且为 [开发准则](开发准则.md) 要求，必须保留并扩展到新浮层。
- 主题偏好持久化、输入法组合态保护、滚动位置记忆、Markdown 安全预览、手记图片图集（V1.5 已交付）。
- 这些能力的对外表现要服从基准的视觉语言；基准未画到的部分按其设计令牌推导，不自创风格。

**C. 已裁决的冲突**

[界面与交互基准](界面与交互基准.md) 中与原型不一致的条目（品牌副标题、卡片标题行数、断点与最小窗口、主题切换实现与时长、模块切换时长、搜索空查询分组命名）已按第 3.1 节的口径逐条处理并写入该文档，不再存在两份互相矛盾的界面规范。

## 5. 被回滚工作的处置

事实（已复核）：

- `backup/v2-broken`（`9f980c8`）与其父 `3c8c364` 曾实现知识归纳/多重收录、设置页与单条导出；另有一个悬挂提交与一个 `stash` 装着未完成接线。
- 独立复核在临时克隆中重建整套栈后测试全绿，说明**功能代码本身并非不可用**；真正导致「应用完全不可用」的是工程组织：`SCHEMA_VERSION` 被改成 4，而 `migrations/004_threads.sql` 处于**未跟踪**状态，同时新增了「迁移文件数必须等于 `SCHEMA_VERSION`」的硬校验——任何 `git clean`/`checkout` 抹掉未跟踪文件，启动即失败。该硬校验正是 [阶段 1 设计](阶段1设计-知识归纳.md) 第 1 节警告过的反模式。

处置决定：**不复活其代码**，阶段 1 从零重写；[阶段 1 设计](阶段1设计-知识归纳.md) 与本地备份分支 `backup/v2-broken` 保留作追溯与对照。重写时数据模型与原型一致（归纳-手记多对多、动态与事务级引用各一张关联表），但接线与界面一律按本文第 3 节实现。

## 6. 迁移与版本契约（本次事故的硬性约定）

1. 迁移文件、模式版本常量与所有调用点必须在**同一个提交**内；**禁止让迁移文件处于未跟踪状态**，提交前用 `git status` 确认。
2. 期望模式版本由**显式声明**给出，不再用「迁移目录文件个数」推导；迁移执行器只保留「版本不能高于迁移文件数」的上界检查，并区分「库比程序新」（拒绝打开并说明）与「程序比库新」（正常升级）。
3. 备份清单里的模式版本必须与同一常量同源，避免两处漂移。
4. 每个阶段的交付说明必须写明数据兼容范围与恢复方式；代码回退不等于数据回退。
5. 代码回退 runbook：`git reset` 回退代码 → 若数据库 `user_version` 高于当前迁移数，**先备份 `memocraft.sqlite` 连同 `-wal`/`-shm`** → 降级 `user_version` 并移除新表 → 复核 `PRAGMA integrity_check` 与 `PRAGMA foreign_key_check`。

## 7. 验证门禁

| 层次     | 要求                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| 每阶段   | `pnpm check`（类型、lint、格式、单元与真实 SQLite）→ `pnpm check:full`（追加普通 tsc、构建、Electron 运行时） |
| 涉及界面 | `pnpm test:e2e` 桌面流程；新增模块的关键路径进入自动化，并保持既有草稿、保存失败与焦点恢复覆盖                |
| 涉及打包 | `pnpm run package:dir` 重新打包后再做包内验证，不得引用过期的 `release/` 产物                                 |
| 视觉核对 | 与第 3 节逐项对照，含浅色/深色两套、专注模式、空状态、动效与键盘绑定；截图留档                                |
| 数据     | 真实 SQLite 集成测试覆盖多对多、唯一约束、幂等关联、软删除可见性组合与失败回滚                                |

环境约束（实测）：桌面流程需要 Electron 启动 Chromium 子进程并初始化自身沙箱，在本会话默认沙箱下必然失败；需要在放宽限制的终端运行，或由维护者在本机终端执行。无法运行的项目必须在交付说明中标注为「未运行」。

## 8. 风险与未决

1. **基准文档的持续同步**：[界面与交互基准](界面与交互基准.md) 已按裁决口径改写，两份规范不再互相矛盾；后续每个阶段改变界面时，必须同步该文档，避免再次出现规范与实现不一致。
2. **界面设计缺口**：回收站页面、备份/恢复/导出入口、设置（含外观偏好落盘）在基准中没有对应界面，需要先出设计再实现；否则会出现「按基准做不出来」或自行发挥两种情况。
3. **对齐不等于降级**：基准缺少焦点管理、失败保留、输入法保护等能力，实现时按 3.3B 保留；不得为了「和原型一样」而削掉既有质量与无障碍行为。
4. **单一保存闸门**：当前全站共用一个 `busy` 状态与切页前统一落盘，四模块共用会互相阻塞；阶段 1 引入归纳编辑现场前必须重新审视。
5. **规模未知**：现在一次加载全部手记、搜索上限 50 条；阶段 3 之前先测量真实数据量。
6. **恢复是唯一替换活动数据的操作**，失败路径验证优先级高于新功能。
7. **多会话并发**是本次事故的真实成因；阶段内保持单写入者，不重开已验收阶段的既有文件。
8. **平台**：只有 macOS arm64 证据，Windows 需独立环境，不得在无证据时声明支持。
9. **文档同步成本**：产品规格（含撤销交互）、架构与实施、界面与交互基准、项目结构需随各阶段同步更新，避免再次出现文档与实现不一致。

## 9. 明确不做

- 嵌套归纳、手动排序、收纳置顶与颜色标记、归纳内批量操作。
- 动态手帐视图、依赖图、自动生成当前概况、跨事务移动动态、手记历史版本快照。
- 自定义大分类、截止日期、提醒、子任务、待办勾选或额外进度字段。
- 多草稿管理、收件箱模块、无限画布、白板、自动同步、完整修订历史、插件系统、AI 与语义搜索。
- 永久删除与自动清空回收站。
- 图片压缩、格式转换、OCR、图片搜索、跨手记复用与嵌入正文。
