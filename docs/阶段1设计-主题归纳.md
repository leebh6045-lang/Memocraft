## 1. 开工前必须修的一处缺陷

加迁移 003 时会立刻失败，原因不在归纳，而在现有的模式版本校验：

`src/storage/note-store.ts` 构造时执行 `requireMigrationVersion(this.database, listMigrations(options.migrationsDirectory).length)`。它把「迁移目录里的文件个数」当成数据库应有的模式版本，只对「目录内容与数据库出自同一次发行」的常见情况成立。两种真实场景会误报：

1. 数据库已按旧版本迁移完，但提供的迁移目录比它新。现有集成测试就在跑这个场景：复制 001/002 后追加 `003_index.sql`，库停在 2、目录长度 3 → 判定为「模式版本与当前应用不一致」并抛错。
2. 将来任何「用一份迁移目录去恢复另一版本的库」的路径都会踩到同一处。

修法：把期望版本改成显式入参，不再从目录长度推断。

```ts
export class NoteStore {
  constructor(options: {
    dataDirectory: string;
    migrationsDirectory: string;
    /** 本应用的数据结构版本；迁移执行完成后数据库必须等于它，否则拒绝打开。 */
    expectedSchemaVersion: number;
  });
}
```

调用方（`storage-worker.ts`）用共享常量传入，`NoteImageStore` 的 `REQUIRED_SCHEMA_VERSION` 一并改为引用同一常量，避免两处各写一个数字：

```ts
// src/storage/schema.ts
/** 当前应用的数据结构版本；每新增一个迁移文件时同步加一。 */
export const SCHEMA_VERSION = 3;
```

迁移管理器保留「版本不能高于迁移文件数」的检查（防止用旧应用打开新库），但不再要求两者相等——追加迁移后旧库能正常升级，这正是迁移存在的意义。本项作为阶段 1 的**前置修复**单独完成并验证，不与归纳功能混在一个改动里。

## 3. 数据模型

新增迁移 `migrations/003_topics.sql`：

```sql
CREATE TABLE topics (
  id TEXT PRIMARY KEY NOT NULL,
  title TEXT NOT NULL CHECK (length(trim(title)) > 0),
  description TEXT NOT NULL DEFAULT '',
  revision INTEGER NOT NULL CHECK (revision >= 1),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT
) STRICT;

CREATE INDEX topics_updated_at ON topics(updated_at DESC, id DESC) WHERE deleted_at IS NULL;

CREATE TABLE note_topics (
  note_id TEXT NOT NULL REFERENCES notes(id),
  topic_id TEXT NOT NULL REFERENCES topics(id),
  created_at TEXT NOT NULL,
  PRIMARY KEY (note_id, topic_id)
) STRICT;

CREATE INDEX note_topics_topic_id ON note_topics(topic_id);
```

设计说明：

- **`revision` 用于并发保护**，与手记、图片的取向一致：编辑请求带 `expectedRevision`，同内容重试视为成功，其他版本差异视为冲突并保留本地输入。归纳的说明是长文本、可能自动保存，没有它就会出现「旧窗口覆盖新内容」。
- **关联表用复合主键而不是额外的 id**：一个 `(note_id, topic_id)` 只存一行，重复收录由约束挡住，不需要业务层先查后写。
- **不存 `position`**。产品规格明确「首版不做手动排序」，所以收录顺序不作为持久状态；归纳内按手记创建时间倒序，与手记一致。
- **`created_at` 记录收录时间**，供「最近收录」这类基于真实时间的展示使用，也便于排查。它与 sort_key 无关，不是排序字段。
- **外键指向实体表**，让数据库拒绝指向不存在手记的收录行。软删除与它不冲突：删除是标记时间，行仍在。
- 不需要 `ON DELETE` 级联：本产品不做物理删除（[架构与实施](架构与实施.md) 第 3.4 节）。

## 4. 领域与校验

新增 `src/domain/topic.ts`：

```ts
export interface Topic {
  id: string;
  title: string;
  description: string;
  revision: number;
  createdAt: string;
  updatedAt: string;
}

export interface TopicSummary extends Topic {
  /** 该归纳当前收录的有效手记数量。 */
  noteCount: number;
}

export interface TopicEdit {
  id: string;
  title: string;
  description: string;
  expectedRevision: number;
}

/** 一条手记被哪些归纳收录，用于手记侧反查。 */
export interface TopicMembership {
  noteId: string;
  topicIds: string[];
}

/** 轻量索引：界面对「这条手记属于哪些归纳」做即时判断，不需要每次都问数据库。 */
export interface TopicIndexEntry {
  topicId: string;
  noteIds: string[];
}
```

`src/services/validation.ts` 增加：

- `validateTopicCreate`：标题必填、去两端空白、不超过 300 字符（与手记标题同一上限）；说明不超过 2000 字符；可选 `confirmDuplicate` 必须为布尔。
- `validateTopicEdit`：在上述基础上要求合法 UUID 与 `expectedRevision >= 1`。
- `validateTopicMembership`：`topicId`、`noteId` 均为合法 UUID。

数据库层的 CHECK 只做兜底（非空标题），长度与格式由服务层判定，避免把字符长度语义写进 SQL 迁移。

## 5. 存储层

新增 `src/storage/topic-store.ts`，构造函数接收与 `NoteStore` 共用的一条连接：

```ts
export class TopicStore {
  constructor(database: DatabaseSync) {}
  list(): TopicSummary[];
  detail(topicId: string): { topic: TopicSummary; notes: Note[] };
  create(input: { title: string; description: string; confirmDuplicate: boolean }): Topic;
  /** 同名时抛出带候选信息的错误，由界面确认后带 confirmDuplicate 重试。 */
  update(edit: TopicEdit): Topic;
  remove(topicId: string): void;
  addNotes(topicId: string, noteIds: string[]): TopicMembership;
  removeNote(topicId: string, noteId: string): TopicMembership;
  index(): TopicIndexEntry[];
  membership(noteId: string): string[];
}
```

要点：

- **连接所有权仍在 `NoteStore`**，`TopicStore` 只使用不关闭，与 `NoteImageStore` 同一模式（[V2 架构决定](decisions/002-V2架构决定.md) 第 1 条）。
- **收录与移出在事务内完成**，并先校验手记与归纳都存在且未被删除。外键不能代替这项业务规则，因为删除是软删除。
- **`addNotes` 幂等**：重复收录同一配对不产生第二行（`INSERT ... ON CONFLICT DO NOTHING`），也不改 `created_at`。
- **同名处理**：`create` 与 `update` 在事务内查同名（`title = ? AND deleted_at IS NULL`，含大小写与空白的规范化比较规则见下），命中且未带 `confirmDuplicate` 时抛出 `AppError('CONFLICT', ...)`，消息里说明已有同名归纳、由界面询问用户；带确认则继续创建。允许多个同名归纳，稳定 ID 才是标识。
- **`detail` 里的手记读取**复用 `NoteStore` 的映射逻辑而不是复制一份 SQL：`TopicStore` 接收一个读取手记的最小函数作为依赖，避免两处各写一套行映射。
- **`remove` 只标记 `topics.deleted_at`**，不动 `note_topics`，也不改动手记。恢复后收录关系原样回来（测试覆盖）。

## 7. 界面

新增页面 `src/renderer/src/pages/TopicsPage.vue`，自行管理「列表 / 详情」两级视图（不引入路由库，与现有 `App.vue` 的模块切换方式一致）：

- **列表**：平级列表，显示标题、说明摘要、收录数量、更新时间；顶部「新建归纳」；空状态说明归纳的用途并给出入口。
- **详情**：「返回列表」、可编辑的标题与说明（沿用抽屉的自动保存与状态反馈模式：正在保存／已保存／失败保留输入）、操作区「收录手记」。
- **所收录手记**：复用 `NoteCard`，按手记创建时间倒序，点击打开手记抽屉；空状态给出「收录已有手记」与「去写一条」两个入口。
- **收录选择器** `NotePicker.vue`：浮层内搜索手记（复用现有 `search` 能力与 `useModalFocus`），支持多选后一次提交；已在归纳中的手记显示为已收录且不可重复选择。

首页的「新建归纳」由禁用改为可用：进入归纳模块并直接打开新建表单。归纳模块的导航项不变。

手记抽屉 `NoteDrawer.vue` 中把占位文案换成真实内容：

- 「收录于归纳」列出所属归纳（可点击跳到该归纳），提供「收录到归纳…」按钮打开同一个选择器（选择器需要支持「选已有归纳」，这是它在归纳侧没有的用法）。
- 移出操作放在归纳标签旁，成功后即时从列表移除。

## 8. 界面如何保持最新

归纳索引由渲染端持有（`loadTopicsIndex` 的返回值），因此**所有收录与移出都作用于同一份索引**，归纳列表的收录数量、抽屉里的所属归纳、选择器的已收录状态会同时更新，不需要新增全局刷新信号。

这与当前手记列表的做法一致（手记列表也是渲染端持有、局部更新）。不引入全局事件总线或响应式 store：只有当出现第二个数据持有者时才需要，现在没有。

`SearchPalette` 依赖的 `changeVersion` 仍然只在手记变化时递增，归纳的改变不影响它。
