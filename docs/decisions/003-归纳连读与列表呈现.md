# 归纳连读与列表呈现

日期：2026-09-28

## 问题

归纳详情原本只有两列卡片，读一个主题时看不到每条手记的记录时间，也没有「连着读一遍」的形态；手记的呈现控件和标签筛选挤在同一段左侧，阅读流还要用户自己决定是否按时间分段。同时归纳内的卡片因为在网格里外包了一层容器而按内容收缩，收录越多越显得东倒西歪。

## 选择

1. **归纳详情只保留「连读」与「网格」两种呈现**，默认连读。归纳的用途是读一个主题，按时间与阅读流已由手记承担；选项越少，页头越干净。网格保留为退路，同时保留悬停「移出」。
2. **连读是文档而不是列表**：每条手记一个带序号的小节，右侧固定「本页目录」随滚动高亮，点击目录平滑滚动并让开固定标题栏；小节被悬停或键盘聚焦时才出现「打开」与「移出」。顺序提供「最新在前 / 最早在前」，默认仍是产品规格要求的最新在前。
3. **阅读流固定按时间分段**，去掉勾选框；分段方式与「按时间」共用一项。首版让用户自己组合两种维度，实际使用时只是多了一次选择，去掉后行为更稳定。
4. **列表缩略图走新的只读批量接口**（`loadImageIndex`），只取 ID、显示名、原名与宽高，不含路径与字节；缩略图仍由 `memocraft-image` 协议按 ID 取图。列表要显示图片，但不应因此把附件路径或字节带进渲染端，也不应让每条手记各发一次请求。
5. **归纳详情的呈现与顺序各自存本机**，与手记呈现、归纳目录排列同一做法；读取失败退回默认，写入失败照常切换并提示。

## 代价

- 归纳详情多了一套文档式排版与滚动联动，组件与样式都更长；窄窗需要单独处理（隐藏右侧目录）。
- 缩略图带来一次批量查询：手记很多时按 200 条分批请求，启动时会有几毫秒到几十毫秒的额外读取；图片摘要按手记 ID 常驻渲染端内存。
- 「摘要跳过被当作标题的首行」是展示规则变化：没填标题的手记，卡片摘要会比以前少一行。
- 归纳详情的默认呈现由卡片变为连读，属于可见的行为变化，已同步产品规格与界面基准。

## 重新评估条件

- 阅读流或连读在真实数据量下出现滚动卡顿，改为按可见区渲染。
- 归纳重新需要「按时间 / 阅读流」其中一种呈现时，先确认它与手记的分工是否仍然成立，再考虑把两种页面的呈现选择合并成一套。
- 若附件规模增长到缩略图批量查询明显拖慢启动，改为按当前可见列表按需请求。
