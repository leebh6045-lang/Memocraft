# 005：DeepSeek 接入与凭据边界

## 问题

三个 AI 功能需要共用模型配置、请求与错误处理；页面不应持有已保存密钥或直接访问外部 API。当前知识库恢复会整体替换数据目录，不能将本机凭据混在被替换的目录内。旧规划采用 Anthropic，当前需求已确定为 DeepSeek。

## 选择

- 第一阶段只接 DeepSeek 官方 Chat Completions；默认 `deepseek-flash`，可选 `deepseek-v4-pro`。
- renderer 经有限 preload API 调用主进程服务；数据库由已有 worker 唯一连接处理。
- 模型保存在知识库 SQLite，密钥通过 safeStorage 加密，存于知识库外的独立凭据目录。
- 模型选择与保存密钥分开提交，避免为两种介质建立不可靠的跨资源事务。
- 通过 Electron 网络栈发起请求，沿用系统代理；不自动重试计费请求。
- 连接测试必须取得完整的非空生成回答；模拟应答与真实供应商验证分别记录。
- 每阶段先有任务书与设计文档，验收后更新实际状态。

## 原因与代价

密钥不进入数据库备份，换机需要重新输入；本机恢复知识库保留密钥，模型则随备份恢复。系统加密不可用时拒绝保存与调用，避免明文降级。首轮只有一个供应商，不建立插件注册中心或通用依赖注入框架；使用内置能力不新增 SDK。

## 重新评估条件

接入第二个供应商、出现复杂流式响应需求或多个 AI 业务任务并发后，再评估供应商适配和请求调度。后续业务的上下文检索、来源校验与总结缓存由各阶段设计独立说明。
