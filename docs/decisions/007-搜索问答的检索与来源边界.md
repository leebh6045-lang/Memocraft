# 007：搜索问答的检索与来源边界

## 问题

阶段三把「问一句话，得到基于自己记录的答案」做进搜索面板。与阶段二归纳建议相比，此阶段有四个新的边界问题：

1. 现有检索是整串子串匹配，无法处理自然语言问句，检索层怎么建；
2. 答案里的「来源」如何从模型输出安全地映射回真实手记；
3. 回答长度与错误处理的策略是否沿用阶段二；
4. 问答要不要发送图片。

## 选择

### 一、新建手记专用检索入口，不扩展已有 `SearchStore`

新增 `NoteSearchStore`，做「本地切词 → 多词 `LIKE` 命中 → 字段加权聚合排序 → 命中窗口摘录」。

不与现有 `SearchStore` 合并，因为两者目标不同：现有搜索是界面导向的（四类对象合并、每类 20 条、只按更新时间排序），问答需要的是手记专用、字段加权（标题 3 / 标签 2 / 正文 1）、多词聚合（命中词数优先）的排序。混在一起会让现有搜索的既有测试基准（`search-scale.test.ts` 的 400ms 预算）失去意义。

切词（`extractTerms`）放在服务层而不是存储层：它是纯函数，便于单测，且存储层应只负责查询。

**明确接受这是关键词匹配，不是语义检索。** 同义改写命中不了。首版的处理是「没命中就说没找到」，不编造答案。向量召回与 FTS5 都留到规模或质量实际不足时再评估。

### 二、无命中时短路，不调用模型

检索结果为空直接返回 `{ answer: '', sources: [], matchedNotes: 0 }`，不发请求。

这是与阶段二建议的一处实质差异：建议总得调用模型（有正文就有判断依据），而问答可能根本没有检索依据。为一个已知不会有依据的问题付费是纯粹的浪费，而且模型在没有摘录的情况下极易用外部知识作答——那恰恰是本功能最该避免的行为。

### 三、来源编号由本地映射，模型只给展示编号

prompt 中的手记用本次展示编号 `[1]`、`[2]` 标注，模型只返回 `sources: [1, 3]`。主进程校验编号是否落在 `1..hits.length` 内，映射为真实 UUID，标题由本地回填。

**不让模型输出手记 ID**：手记 ID 是 UUID，模型无法可靠复现，让它输出等于把「能否正确引用」建立在一个它做不好的任务上。**也不从回答正文里解析 `#\d+`**：正文中的编号可能被模型随意改写，且无法区分引用与普通数字。

越界编号丢弃而非整份拒绝，与阶段二对未知归纳 ID 的处理一致。

### 四、回答超长截断，来源越界丢弃，结构错误拒绝

三种问题的处理策略不同，依据「错误是否影响数据正确性」：

- **结构错误**（非 JSON、缺字段、类型不符）→ 整份拒绝。结果整体不可信。
- **回答超长**（> 400 字符）→ 截断并附省略号。回答是纯展示内容，超长只影响排版。这与阶段二「标签越界整份拒绝」不同——标签会被采纳进草稿成为数据，回答不会。
- **来源编号越界** → 丢弃该编号。局部错误，其余可用。
- **来源全部越界** → `sources` 为空，但**回答照常展示**。模型可能给出了正确的概括而只是编号写错，丢掉回答的代价比丢掉来源大。

### 五、不做流式输出

这与阶段一评审时的判断相反，特此记录改判理由：问答的回答是 `{answer, sources}` 结构化 JSON，来源映射依赖完整 JSON；流式增量文本中提取半截 `sources` 数组不可靠。回答限制在 3 句，2–5 秒加载可接受。

阶段一评审曾建议「进入 RAG 前先加流式以改善等待体验」。当时把「改善等待」作为主要收益，但忽略了流式与结构化输出的冲突。改为：本阶段不做流式；若未来回答变成开放式长文本（例如周期总结的叙述性概要），再单独评估。

### 六、本阶段问答不发送图片

阶段二的图片参与是为「一份草稿的即时判断」设计的，触发由用户主动点击，频率有界。问答的触发频率高得多——搜索词每变化一次就可能是一次请求，且一次问答会命中多条手记。逐条送图会让费用随输入频率而不是随知识库规模增长。

周期总结的图片预算天然有界（按「一段时间内的手记数」），因此图片参与留到阶段四与周期总结一起设计，那时可以统一回答「一次请求最多带几张图、总预算怎么分」。`AiImageReader` 已按跨阶段共享的方式建好（见决策 006 第七条），阶段四直接复用。

### 七、检索范围只含手记，不含草稿与回收站

与现有搜索一致：草稿不参与任何检索，已删除手记不出现在结果里，归档不属于手记范畴。归纳、事务、动态也不参与——问答回答的是「我的记录里怎么说」，混入事务动态会让来源类型难以在摘要行里表达。

## 原因与代价

- 关键词检索而非语义检索，代价是问法换一种就可能命中不了；收益是零额外依赖、可解释（用户能看出为什么命中）。同义改写问题在真实使用中若明显影响体验，再评估向量召回。
- 无命中短路省下计费，代价是用户可能因为检索没命中而误以为「我没记过」。界面文案因此写成「你的手记里还没有关于这个的记录」而不是「没有找到答案」——如实说明是检索没命中。
- 来源映射让模型只做它擅长的事（概括），引用由本地保证正确。代价是 prompt 里必须解释 `[1]` 的含义，且模型仍可能编造编号（由映射丢弃兜底）。
- 不做流式后，长等待没有渐进反馈。缓解方式是加载文案明确（「正在从你的手记中查找…」）且用户可以继续操作搜索结果。
- 问答不发图片意味着带截图的手记只能靠文字正文参与问答。这是本阶段接受的限制，阶段四会重新处理。

## 重新评估条件

- 知识库规模增长到检索耗时明显（例如超出现有 400ms 预算的一个数量级）时，评估 FTS5 全文索引。
- 同义改写的命中率在实际使用中明显不足时，评估本地嵌入与向量召回。
- 回答需要超过 3 句、或周期总结的概要需要叙述性长文本时，重新评估流式输出与 `sources` 的契约形态。
- 阶段四设计周期总结时，需要一并确定「一次请求的图片预算如何在多条手记间分配」，以及是否把这套规则反向应用于问答。
