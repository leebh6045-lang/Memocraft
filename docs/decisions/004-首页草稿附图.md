# 首页草稿附图

日期：2026-09-28

## 问题

图片原本只能归属已保存的手记：`note_images.note_id` 是 `NOT NULL` 外键，界面也明确提示「先保存这条手记，再加入图片」。用户实际写一条带图手记时要先保存、再打开详情、再加图，多出两步。

直接放开的难点是归属：草稿不是手记，图片先写给谁；以及保存手记与图片转移必须一起成功，否则会留下「有手记没图」或「图还挂在草稿上」。

## 选择

1. **图片可以归属草稿**：`note_images` 增加 `draft_id`（外键指向 `note_drafts(id)`），`note_id` 放宽为可空，用 `CHECK ((note_id IS NULL) <> (draft_id IS NULL))` 保证恰有其一。序号约束按归属各一份（`UNIQUE (note_id, position)` 与 `UNIQUE (draft_id, position)`）。
2. **保存手记时转移，且在同一事务内**：`NoteStore.commitDraft` 接收一个 `claimDraftImages` 回调，由服务层传入 `NoteImageStore.claimDraftImages(draftId, noteId)`；顺序是「插入手记 → 图片改归属 → 删除草稿行」，任一步失败整体回滚。草稿草稿行由外键挡住：不先转移就删不掉草稿。
3. **图片在添加那一刻就落盘**：文件写进 `attachments/`、元数据写进 `note_images`，草稿内容仍照旧自动保存。不在内存里暂存用户刚选的图，异常退出后图片与草稿都还在。
4. **草稿行必须先存在**：草稿行由自动保存写入，而自动保存会跳过「内容没变」的情况。图集入口因此调用 `useLibrary.ensureDraftStored()`——总是写一次草稿，拿到「归属存在」这个事实后再写图片；失败就明确提示，不写入无法归属的图片。
5. **一套图集操作服务两种归属**：`ImageOwner = { kind: 'note' | 'draft'; id }` 贯穿契约、校验与渲染端，图集的加载、添加、命名、移出都只写一遍；放大层抽成 `ImageViewer`，首页草稿、手记详情与归纳连读共用。

## 代价

- 迁移 `005_draft_images.sql` 需要重建 `note_images`（SQLite 不能直接放宽 NOT NULL），旧库升级时复制全部现有行；模式版本从 4 升到 5，代码回退时数据库不能一起回退。
- `commitDraft` 多了一个回调参数，事务边界仍在一个地方（`NoteStore`），但阅读时需要跟着服务层看一步。
- 草稿附图会一直留在库里直到被保存或移出：被丢弃的草稿（例如恢复备份替换整库）会留下孤儿文件，这与软删除图片的既有处置一致，不做自动清理。

## 重新评估条件

- 若将来支持多草稿或多个窗口同时编辑，`draft_id` 与外键目标需要重新设计，而不是在单槽位草稿上叠加字段。
- 若附件目录出现明显冗余，再评估孤儿文件的清理策略（必须先有可核对的引用关系，不做静默删除）。
