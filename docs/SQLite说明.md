# SQLite 说明：Memocraft 的正式本地数据库

> 2026-09-20。面向初次接触数据库的阅读说明。本文解释概念，不表示数据库和应用已经实现。
> 项目行为见 [需求规格说明书](产品规格.md)，工程方案见 [v1开工总纲](架构与实施.md)。

## 1. SQLite 到底是什么

**SQLite 是正式的关系型数据库引擎，可以长期保存正式业务数据。** 它既可以被用作临时缓存，也可以作为应用的主要数据库；用途取决于应用如何使用它。Memocraft 将它作为正式主库。

“本地”描述数据的位置，“临时”描述数据的生命周期，两者不是一回事。把知识保存到自己电脑的 SQLite 文件中，关掉应用、重启电脑后仍然存在，不会因为程序退出而自动清空。

SQLite 是“嵌入式”数据库：数据库引擎作为一个库被应用调用，不需要另装并启动独立数据库服务器。开发者通过驱动调用引擎，用户日常只需要安装和使用 Memocraft。

可以区分三个名称：

| 名称       | 是什么                               | 本项目中的例子             |
| ---------- | ------------------------------------ | -------------------------- |
| SQL        | 操作关系型数据库的一种语言           | 查询、插入、更新手记的语句 |
| SQLite     | 理解 SQL、管理存储与事务的数据库引擎 | 应用调用的本地数据库能力   |
| 数据库文件 | 引擎管理的实际数据                   | `memocraft.sqlite`         |

文件扩展名可以是 `.sqlite`、`.db` 等，扩展名不会决定是否临时。SQLite 也支持显式创建 `:memory:` 内存库或临时库，这些才具有相应的临时生命周期；正式知识数据使用明确路径下的磁盘数据库。

## 2. 它与 MySQL、PostgreSQL 有什么区别

| 方面         | SQLite                                       | MySQL / PostgreSQL 的典型使用方式              |
| ------------ | -------------------------------------------- | ---------------------------------------------- |
| 运行形态     | 嵌入应用，由应用直接调用库                   | 独立运行数据库服务，应用通过连接访问           |
| 数据位置     | 通常是当前设备上的文件                       | 由数据库服务器管理，可在本机或远程             |
| 部署         | 随应用提供引擎/驱动，无需额外服务            | 安装和维护服务、用户权限与连接配置             |
| 适合的场景   | 桌面、移动端、设备应用及适合其并发模型的服务 | 多客户端共享数据、较高并发写入、集中管理       |
| 正式长期存储 | 可以                                         | 可以                                           |
| 并发特征     | 多个读取者，同一数据库同一时刻仅一个写事务   | 通常能处理更多并发写事务，具体取决于引擎与负载 |

SQLite 并不是“学习阶段先凑合用的数据库”。个人桌面知识库的操作主要来自自己，短事务足以满足这类使用模式。今后手记多了，也不意味着必须立即换数据库，通常先检查查询、索引和实际性能。

如果以后成为多人同时在线编辑同一套数据的服务，才需要重新评估服务器端架构。SQL 方言和应用依赖也有差异，更换数据库不是直接替换文件名。

## 3. 数据库里面怎样放手记

数据库内部有“表”，一张表有多行记录，每行由多个字段构成。可以先把它想成有明确列定义和规则的数据表，但数据库还具备关系、查询、索引与事务等能力。

例如，简化的手记表：

| id  | title      | body                               |
| --- | ---------- | ---------------------------------- |
| n1  | HTTPS 排错 | 检查域名、证书有效期和服务配置……   |
| n2  | npm 命令   | 今天弄懂了一个之前容易混淆的命令…… |

`id` 是稳定身份，标题改名不会改变身份。正文 `body` 可以保存整段 Markdown，其中包括中文、换行、代码块和链接。Markdown 是内容格式，SQLite 是存储方式，它们可以同时使用。

再有一张归纳表：

| id  | title      |
| --- | ---------- |
| t1  | 服务器运维 |
| t2  | 网络安全   |

“同一条手记被两个归纳收录”通过关联表表达：

| note_id | topic_id |
| ------- | -------- |
| n1      | t1       |
| n1      | t2       |

这里没有复制两份 HTTPS 正文。数据库保存一份手记、两个归纳，以及两条关联。修改 n1 的正文，两个归纳查到的都是新内容；移除 n1 与 t1 的关联，n1 和 t2 的关联仍在。

主键保证身份唯一；关联表的联合唯一约束防止同一配对重复；外键限制关联必须指向确实存在的记录。SQLite 使用外键时，我们会在每个连接显式启用它，不依赖默认值。软删除是应用规则，还需要业务层检查，不能只靠外键判断。

## 4. SQL 是怎样参与的

界面点击“查看网络安全归纳”后，业务层可以执行类似这样的查询：

```sql
SELECT n.id, n.title, n.body
FROM notes AS n
JOIN note_topics AS nt ON nt.note_id = n.id
WHERE nt.topic_id = ?
  AND n.deleted_at IS NULL;
```

`?` 由数据库驱动绑定为当前归纳 ID。用户不需要自己写 SQL。实际应用还会验证归纳本身的有效状态、排序和分页；示例只展示“通过关联找内容”的基本原理。

参数绑定可以正确处理引号等输入，也避免把用户内容误当 SQL 代码。数据库本身不理解“这是重要知识”或“这个问题已经懂了”，这些语义由我们定义的字段和应用逻辑表达。

索引类似书后的索引目录，帮助数据库更快找到目标。首版会为常见关联和排序建立必要索引；中文语义理解、同义词搜索或智能回顾不会因使用 SQLite 自动出现，需要另行实现。

## 5. 数据库“事务”为什么重要

这里的数据库事务（transaction）是存储概念，与产品中的“长期事务（Thread）”不同。

假设你在首页保存一条手记，并把它收录到两个归纳，需要完成：

1. 插入手记。
2. 插入与第一个归纳的关联。
3. 插入与第二个归纳的关联。
4. 清除已经转为正式手记的首页草稿。

我们会把它们放进同一个数据库事务中。全部成功才提交；任一步失败，应用回滚整个事务，避免“手记建了一半，草稿却消失了”。执行 SQL 报错后必须正确处理并回滚，不能误以为任何一条语句失败都会自动替应用撤销此前所有操作。

常见的 ACID 四个字母表示：

- 原子性：这组操作作为整体提交或撤回。
- 一致性：提交后仍满足数据库已声明的规则；业务规则也必须由应用正确实现。
- 隔离性：并发读写按数据库的隔离规则进行，不读取另一事务未提交的半成品。
- 持久性：使用正确的事务和持久化配置时，成功提交的数据得到持久保存保障。

SQLite 提供这些数据库能力，但磁盘故障、应用误操作和用户误删仍需要备份应对。数据库事务也不能自动回滚普通文件系统上的附件操作，因此附件写入与恢复需单独协调。

## 6. 点击保存以后，数据去了哪里

```text
首页或手记编辑器中的 Vue 界面
        ↓ 提交内容
preload / IPC 提供的有限接口
        ↓ 校验请求
TypeScript 业务服务与存储层
        ↓ 参数化 SQL 与事务
SQLite 引擎
        ↓
用户数据目录中的 memocraft.sqlite
```

数据库位于应用的用户数据目录，不放进安装程序目录。窗口关闭后数据仍在，下次启动重新打开同一个库。更新程序需要升级数据结构时，运行版本化“迁移”，而不是删掉旧库重新建立。

Electron 自带的 Node 运行时与开发机安装的 Node 是两套运行环境。具体通过 `node:sqlite` 还是其他驱动访问 SQLite，需要在选定 Electron 版本和两个系统的安装包中验证，不在文档阶段假定已经兼容。

## 7. 为什么不用每条手记一个 JSON 文件

JSON 文件也能长期保存数据。SQLite 更适合本次方案的原因，是我们已经有多重收录、引用、待办标记、软删除和恢复等操作。

| 关注点               | 一组 JSON / Markdown 文件    | SQLite 主库                      |
| -------------------- | ---------------------------- | -------------------------------- |
| 直接用文本编辑器阅读 | 容易                         | 通常要通过应用、数据库工具或导出 |
| 一次修改多个对象     | 应用自己协调多文件失败和恢复 | 可以使用数据库事务               |
| 防重复、关联有效性   | 大部分依靠应用代码           | 可以结合唯一约束、外键与业务校验 |
| 复杂查找与组合筛选   | 自行遍历或另建索引           | SQL 查询和索引                   |
| Git 文本差异         | 比较直观                     | 二进制数据库不适合逐行比较或合并 |

因此我们的选择是 SQLite 负责正式结构化存储，同时提供 Markdown 与元数据导出，保证内容能够迁出和独立阅读。导出文件是某个时刻的副本，不要求日常与数据库双向同步。

## 8. 数据库文件、备份和同步

正式数据可以长期保存在一个主数据库文件中，但运行期间可能存在日志文件。启用 WAL 时，新的已提交变化可能暂时仍在 `memocraft.sqlite-wal` 中，另有协调用的 `-shm` 文件；这些由 SQLite 管理。

因此不能在应用仍读写时随便只复制主 `.sqlite` 文件并宣称完成备份。应用应使用经过验证的数据库备份接口生成一致快照，或在正确停止写入、关闭连接之后按可靠流程复制。

完整的 Memocraft 备份还需要包括附件、格式与版本信息。恢复时先验证，再替换活动数据，并保留恢复前的库。可读 Markdown 导出主要服务阅读与迁出，不默认等于可完整还原所有状态的备份。

备份是某个时间点可恢复的副本；同步是多台设备持续交换变化并处理冲突。SQLite 不自带应用级云同步。首版使用备份迁移，两台电脑同时编辑后如何合并，需要以后单独设计。不要让同步软件同时搬运两台正在使用的数据库文件来代替这套设计。

## 9. 对 Memocraft 意味着什么

- SQLite 是长期保存手记、归纳、事务、动态、关系和草稿的正式主库。
- 用户不需要单独安装或管理数据库服务。
- 关应用或重启电脑不会按设计清空数据；删除数据目录或某些卸载清理操作仍会影响本地数据，保存副本很重要。
- 首页草稿与手记都是持久数据，但由不同表与业务规则管理生命周期。
- 一份 SQLite 数据库可以支持应用的全部模块，不需要每个模块另建一个数据库文件。
- 长期保存、备份、导出、自动同步是不同能力，需分别设计和验收。
